# 2. ROS 2 Fundamentals

{{ common }}

Module 1 gave you a robot drawn as boxes and arrows. ROS 2 turns that
drawing into running software: the boxes become **nodes**, the arrows
become **topics**, and this module has you start, inspect and modify a real
system.

## Overview

You will learn the three core ROS 2 building blocks — nodes, topics and
messages — inspect a running system entirely from the command line, and
change a running node's behaviour with a parameter, no restart required.

## Learning objectives

By the end of this module you can:

1. explain what a node, a topic and a message are, and how they relate;
2. inspect a running ROS 2 system from the command line;
3. change a node's behaviour with a parameter and see the effect live.

## Core concepts

### The core ideas, briefly

**Node** — one program doing one job. A LiDAR driver is a node; a path
planner is a node. Nodes start and stop independently.

**Topic** — a named channel carrying messages of one type. Publishers and
subscribers never know about each other directly — asynchronous, one-to-many.

**Message** — the typed structure on a topic: not a Python string, but a
defined type such as `std_msgs/msg/String`, which has a field `data`.

**Package** — the unit you build: nodes, launch files, configuration,
installed together with `colcon`.

```{figure} ../_static/images/diagrams/02-ros2-node-topic-communication.svg
:alt: Two publisher nodes send data to a topic named /scan, which two subscriber nodes read from. A separate pair of nodes shows a two-way service call for contrast.
:width: 100%

Topics decouple publishers from subscribers; services are a direct
request/response between two nodes instead.
```

The decoupling is the whole point: swap the simulator for a real robot, and
every node downstream keeps working, because they only ever agreed on a
topic's **name** and **type**.

### The essential commands

```bash
ros2 node list                 # what is running?
ros2 topic list                # what channels exist?
ros2 topic echo /scan          # what is on this channel right now?
ros2 topic info -v /scan       # who publishes/subscribes, and with what QoS?
ros2 param list /my_node       # what can I configure?
ros2 param set /my_node <p> <v>  # change it, live, no restart
```

These five commands solve most "why is nothing happening?" problems for the
rest of this course. [Full cheat sheet](../reference/ros2-cheatsheet.md).

## Guided example

Try the essential commands above on `turtlesim`, which ships with every
ROS 2 desktop install and needs no separate workspace:

```bash
ros2 run turtlesim turtlesim_node
```

In a second terminal, work through each command against it:

```bash
ros2 node list                            # /turtlesim appears
ros2 topic list                           # look for /turtle1/pose
ros2 topic echo /turtle1/pose             # watch the pose stream live
ros2 param list /turtlesim                # see what is configurable
ros2 param set /turtlesim background_g 177  # change it while the node runs
```

Watch the turtlesim window while you run the last command — the background
colour changes immediately, with no restart. That live effect from a single
`param set` is the same mechanism the practical task below uses on a
different node.

## Practical task

### Goal
Start a prepared publisher node, confirm it works from the command line,
change what it publishes using a parameter, rebuild, and run it again.

### Starting point
A workspace `~/course_ws` containing a package `pubsub_demo` with a working
publisher node `talker.py`, built following the
[installation guide](../prerequisites/installation.md).

### Steps
1. Source the workspace: `source ~/course_ws/install/setup.bash`.
2. Run the node: `ros2 run pubsub_demo talker`.
3. In a second terminal, confirm it: `ros2 topic echo /course_chat`.
4. Inspect it: `ros2 node info /talker` — read what it publishes.
5. Change its message with a parameter:
   `ros2 param set /talker message "hello from ROS 2"`.
6. Confirm the change in the `topic echo` terminal without restarting the
   node.
7. Open `talker.py`, change the default publish rate, rebuild
   (`colcon build --packages-select pubsub_demo`), and run it again.

## Expected result

`ros2 topic echo /course_chat` shows your custom message appearing at the
new rate, without you ever having stopped the original node in step 6.

## Verification

```bash
ros2 topic hz /course_chat
```

The printed rate matches what you set in step 7, within measurement noise.

## Common problems

- **`Package 'pubsub_demo' not found`** — the workspace was not sourced in
  *this* terminal. `source ~/course_ws/install/setup.bash` again.
- **Parameter set has no visible effect** — the parameter was not declared
  in the node (`node.declare_parameter(...)`), so ROS 2 silently ignores an
  undeclared name via `param set`. Check the source.
- **Rebuilt but nothing changed** — a second terminal is still running the
  old node; `Ctrl`+`C` it and start it again after the build.
- **The node runs but nothing is published.** No `rclpy.spin()`, so no
  callback ever fires.
- **`Package 'x' not found` right after building it.** Not sourced in *this*
  terminal, or built in a terminal opened before the build.
- **Changing code has no effect.** Not rebuilt, or rebuilt but an old
  process is still running. `colcon build --symlink-install` avoids this
  for pure Python changes.

## Advanced topics

{{ advanced }}

The core task uses one node started by hand. Real robots start a dozen
nodes together, and not every interaction is a topic.

:::{dropdown} Launch files — starting several nodes at once
:icon: light-bulb

A **launch file** starts nodes together, with parameters and remappings:

```yaml
launch:
- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    name: "sim"
- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    name: "second_sim"
    namespace: "second"
```

```bash
ros2 launch my_package my_launch_file.launch.yaml
```

You will build a real one in [module 8](08-integration.md), where a whole
robot starts from a single command. See the
[full launch file walkthrough](../reference/ros2-cheatsheet.md#launch) for
YAML vs Python launch files and composing them.
:::

:::{dropdown} Services and actions — when a topic is the wrong tool
:icon: light-bulb

A **service** is a request and a response, like a function call across the
network — use it for something quick with an answer: *stand up*, *save the
map*.

```bash
ros2 service call /my_service std_srvs/srv/Empty "{}"
```

An **action** is a long-running task with feedback and the ability to
cancel — use it when the answer takes time: *navigate to this pose*. You
will use one properly in [module 6](06-navigation.md).

```{list-table}
:header-rows: 1
:widths: 20 26 27 27

* -
  - Topic
  - Service
  - Action
* - Pattern
  - Stream, no reply
  - Request → response
  - Goal → feedback → result
* - Duration
  - Continuous
  - Immediate
  - Seconds to minutes
* - Example
  - `/scan`, `/cmd_vel`
  - Stand up, save map
  - Navigate to a pose
```
:::

## Continue learning

:::{dropdown} Parameters, properly — Next step
:icon: light-bulb

**What it is.** Declaring a parameter with a type and a default
(`node.declare_parameter('rate', 10.0)`) instead of relying on an
undeclared name silently doing nothing — the exact failure mode this
module's Common problems section warns about — and reacting to a parameter
change with a callback instead of only reading it once at startup.

**Why it matters.** Every node you write for the rest of this course reads
at least one parameter; getting declaration right now avoids the single
most common "my `param set` did nothing" bug.

**Needs.** This module's practical task.

**Try it.** Add a second, declared parameter to `talker.py` (e.g. a topic
name), register an `add_on_set_parameters_callback`, and confirm the
callback fires on `ros2 param set`.

**Check.** `ros2 param get /talker <your_new_param>` reflects a value you
set live, and your callback's log line appears when you set it.

**Read more.** [ROS 2: using
parameters](https://docs.ros.org/en/humble/Tutorials/Beginner-Client-Libraries/Using-Parameters-In-A-Class-Python.html)
:::

:::{dropdown} Custom message and service types — Next step
:icon: light-bulb

**What it is.** Defining your own `.msg` or `.srv` file in an
`interfaces`-style package when none of the standard `std_msgs` types fit
your data.

**Why it matters.** Real robot data — a detected object with a label and a
confidence, a mission status with a reason string — rarely fits a bare
`String` or `Float64`; this course's own capstone project uses a custom
`mission_status` message shape for exactly this reason.

**Needs.** A working workspace and one built package.

**Try it.** Define a `.msg` file with two fields (e.g. `string label` and
`float64 confidence`), build it, then publish and echo one message of that
type.

**Check.** `ros2 interface show <your_package>/msg/<YourType>` prints your
field definitions, and `ros2 topic echo` shows both fields correctly.

**Read more.** [ROS 2: creating custom msg and srv
files](https://docs.ros.org/en/humble/Tutorials/Beginner-Client-Libraries/Custom-ROS2-Interfaces.html)
:::

:::{dropdown} QoS basics, with a reproducible mismatch — Intermediate
:icon: light-bulb

**What it is.** Quality of Service settings — **reliability**
(`RELIABLE` vs `BEST_EFFORT`) and **durability** (`VOLATILE` vs
`TRANSIENT_LOCAL`) — that a publisher and subscriber must be
*compatible* on, not necessarily identical, or no data crosses at all with
no error message.

**Why it matters.** A QoS mismatch is one of the few ROS 2 failures with
**zero** error output — the node runs, the topic exists, and nothing
arrives. [Module 3's](03-sensors-tf.md#common-problems) "RViz shows nothing"
diagnosis exists largely because of this.

**Needs.** This module's practical task, `talker.py` and a subscriber.

**Try it — reproduce the failure on purpose.** Set your publisher's
reliability to `BEST_EFFORT` and your subscriber's to `RELIABLE` (in
`rclpy`, via a `QoSProfile`), run both, and confirm — with `ros2 topic
echo` on the subscriber's own topic — that nothing arrives, then check
`ros2 topic info -v <topic>` to see the mismatch reported there.

**Check.** You can point at the exact `ros2 topic info -v` output line that
shows the incompatible profiles, and fix it by matching one setting.

**Read more.** [ROS 2: About Quality of Service
settings](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html)
:::

:::{dropdown} Namespaces and remapping — Next step
:icon: light-bulb

**What it is.** Running the *same* node under a different name
(`__node:=second_talker`) or with its topics under a namespace prefix
(`/second/course_chat` instead of `/course_chat`), without changing a line
of code.

**Why it matters.** This is how two identical robots — or two instances of
the same simulated robot — run side by side without their topics
colliding; you already saw the pattern in the "Launch files" dropdown
above (`namespace: "second"`).

**Needs.** This module's practical task.

**Try it.** Run a second instance of `talker.py` with
`ros2 run pubsub_demo talker --ros-args -r __ns:=/second`, alongside the
original.

**Check.** `ros2 topic list` shows both `/course_chat` and
`/second/course_chat` as separate topics from two separate node instances.

**Read more.** [ROS 2: remapping
arguments](https://docs.ros.org/en/humble/How-To-Guides/Node-arguments.html)
:::

:::{dropdown} Lifecycle nodes — Intermediate
:icon: light-bulb

**What it is.** A node with an explicit state machine
(`unconfigured → inactive → active → finalized`) instead of "doing its job
the moment it starts" — you already ran `ros2 lifecycle get` against one in
[module 6](06-navigation.md#core-concepts) without building one yourself.

**Why it matters.** A lifecycle node lets a supervisor (or you, by hand)
control exactly when it starts doing real work — critical for a system
where bring-up order matters, which is the entire subject of
[module 8](08-integration.md#core-concepts).

**Needs.** Comfort with plain `rclpy` nodes.

**Try it.** Convert `talker.py` into a
`rclpy.lifecycle.LifecycleNode`, moving the publisher's creation into
`on_configure` and only starting to publish in `on_activate`.

**Check.** `ros2 lifecycle get /talker` reports `unconfigured` immediately
after launch, and no message appears on `/course_chat` until you call
`ros2 lifecycle set /talker activate`.

**Read more.** [ROS 2: managed
(lifecycle) nodes](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Ros2-Managed-Nodes.html)
:::

:::{dropdown} Node composition — Advanced
:icon: light-bulb

**What it is.** Loading several nodes as plugins into one OS process
(a "component container"), instead of one process per node, so that
messages between them can be passed by pointer instead of copied and
serialized.

**Why it matters.** For a high-rate pipeline — a camera driver feeding a
perception node feeding a detector, all in [module
4](04-perception/index.md) — process-per-node overhead adds real latency;
composition removes most of it.

**Needs.** Two working nodes, in separate packages.

**Try it.** Convert one node into a composable node class and load both it
and a second node into one `component_container` using
`ros2 component load`.

**Check.** `ros2 component list` shows both components loaded into the same
container process.

**Read more.** [ROS 2:
composition](https://docs.ros.org/en/humble/Tutorials/Intermediate/Composition.html)
:::

:::{dropdown} Executors and callback groups — Advanced
:icon: light-bulb

**What it is.** The **executor** is what actually calls your callbacks;
the default single-threaded executor runs them one at a time, which is
usually fine until one callback blocks and starves every other callback in
that node. **Callback groups** (`MutuallyExclusiveCallbackGroup`,
`ReentrantCallbackGroup`) control which callbacks are allowed to run
concurrently against a multi-threaded executor.

**Why it matters.** A node that "randomly stops responding to one topic
while another still works" is very often a single blocking callback
starving a single-threaded executor, not a network or QoS problem.

**Needs.** Comfort with plain `rclpy` nodes and Python threading concepts.

**Try it.** Add a deliberately slow (`time.sleep(2)`) callback to one
subscription in a node with two subscriptions on a single-threaded
executor, and observe the second subscription's callback stall too; then
switch to a `MultiThreadedExecutor` and confirm it no longer does.

**Check.** You can explain, from what you observed, which executor and
which callback-group setting fixed the stall.

**Read more.** [ROS 2: executors and callback
groups](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Executors.html)
:::

:::{dropdown} Automated tests for ROS 2 packages — Advanced
:icon: light-bulb

**What it is.** Unit tests for plain Python logic via `pytest`
(no ROS 2 needed), and integration tests via `launch_testing`, which starts
real nodes and checks what they publish — both run automatically by
`colcon test`.

**Why it matters.** A change that breaks a node's behaviour should fail a
test, not get discovered when the [capstone project](hackathon.md) breaks
in front of you — this is what [module 8's](08-integration.md#core-concepts)
"reproducible" standard looks like applied to code instead of launch
files.

**Needs.** A working package with at least one node.

**Try it.** Write one `pytest` unit test for any pure-Python helper
function in your package, then run `colcon test --packages-select
pubsub_demo` and read the result summary.

**Check.** `colcon test-result --verbose` shows your test passing (or
correctly failing, if you deliberately broke the function first to check
the test actually catches it).

**Read more.** [ROS 2:
launch_testing](https://github.com/ros2/launch/tree/humble/launch_testing) ·
[colcon test](https://colcon.readthedocs.io/en/released/user/quick-start.html#test-packages)
:::
