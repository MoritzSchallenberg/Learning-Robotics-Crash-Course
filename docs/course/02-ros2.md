Last week you drew a robot as boxes and arrows. ROS 2 is what turns that
drawing into running software: the boxes become **nodes**, the arrows become
**topics**, and the whole thing becomes something you can start, inspect and
modify while it runs.

## Learning objectives

After this session you can:

- create a workspace and a package, and build them with `colcon`;
- write a ROS 2 node in Python and run it;
- publish and subscribe to a topic;
- declare and change parameters at runtime;
- start several nodes at once with a launch file;
- inspect a running system from the command line;
- explain when to use a service or an action instead of a topic.

## Prerequisites

[Installation](../prerequisites/installation.md) complete: `echo $ROS_DISTRO`
prints your distribution, and `ros2 run turtlesim turtlesim_node` opens a
window.

## The core ideas

**Node** — one program doing one job. A LiDAR driver is a node; a path planner
is a node. Nodes start and stop independently, and one crashing does not take
the others down.

**Topic** — a named channel that carries messages of one type. Nodes publish to
it and subscribe to it without knowing about each other. This is asynchronous
and one-to-many: the LiDAR driver publishes `/scan` and does not care whether
nobody or five nodes are listening.

**Message** — the typed structure that travels on a topic. Not a Python string
but a defined type, such as `std_msgs/msg/String` which contains a field
`data`.

**Package** — the unit you build and install. It holds nodes, launch files and
configuration.

**Workspace** — the directory where you build your packages.

The decoupling is the whole point. You can replace the simulator with a real
robot, and every node downstream keeps working, because they only ever agreed
on the name and type of a topic.

## Workspaces and packages

### Creating a workspace

```bash
mkdir -p ~/robot_ws/src
cd ~/robot_ws
colcon build
```

That produces `build/`, `install/` and `log/` next to `src/`. Source the
result so ROS 2 can find what you build:

```bash
source ~/robot_ws/install/setup.bash
```

### Creating a package

```bash
cd ~/robot_ws/src
ros2 pkg create --build-type ament_python my_first_package --dependencies rclpy
```

`--build-type` is `ament_python` for Python packages and `ament_cmake` for
C++. This course uses Python throughout.

Inside your new package you will find:

`package.xml`
: metadata and dependencies

`setup.py`
: how the package is installed, and — importantly — which scripts become
  runnable nodes

`my_first_package/`
: a subdirectory with the same name as the package, where your Python files go

:::{warning}
Python files must live in the subdirectory that matches the package name. Put
them elsewhere and `ros2 run` will not find them, with an error that does not
explain why.
:::

### Finding things

```bash
ros2 pkg prefix turtlesim       # where is this package installed?
echo $AMENT_PREFIX_PATH         # in which order are packages searched?
```

`$AMENT_PREFIX_PATH` is worth understanding: your workspace appears *before*
`/opt/ros/<distro>`, so a package you build shadows a system package of the
same name. Handy when intended, baffling when not.

## Writing a node

The smallest useful ROS 2 node in Python:

```python
#!/usr/bin/env python3

import rclpy


def main():
    rclpy.init()
    node = rclpy.create_node('firstnode')
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

Line by line:

- `rclpy.init()` starts the ROS 2 client library.
- `rclpy.create_node('firstnode')` creates the node. `firstnode` is the name it
  will have in the running system — not the name of the file, and not the name
  of the executable.
- `rclpy.spin(node)` hands control to ROS 2, which now calls your callbacks
  whenever there is something to do. Without a `spin`, no callback ever runs.
- The `try`/`except KeyboardInterrupt` lets `Ctrl` + `C` shut the node down
  cleanly instead of dumping a traceback.
- `destroy_node()` and `shutdown()` tell the ROS 2 graph the node is gone.

### Making it runnable

Save the file as `my_first_package/myfirstnode.py`, then add an entry point in
`setup.py`:

```python
entry_points={
    'console_scripts': [
        'emptynode = my_first_package.myfirstnode:main',
    ],
},
```

This says: create an executable called `emptynode` that calls `main` in
`my_first_package/myfirstnode.py`.

Build, source, run:

```bash
cd ~/robot_ws
colcon build
source install/setup.bash
ros2 run my_first_package emptynode
```

It does nothing visible. Check that it exists, from a second terminal:

```bash
ros2 node list        # shows /firstnode
ros2 node info /firstnode
```

## Topics: publisher and subscriber

### A publisher

```python
#!/usr/bin/env python3

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MyPublisher(Node):

    def __init__(self):
        super().__init__('myfirstpublisher')
        self.publisher = self.create_publisher(String, 'myfirsttopic', 10)
        self.create_timer(0.1, self.timer_callback)

    def timer_callback(self):
        message = String()
        message.data = 'Hello ROS 2 communication'
        self.publisher.publish(message)


def main():
    rclpy.init()
    node = MyPublisher()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

`create_publisher` takes three arguments: the message **type**, the topic
**name**, and the queue depth (or a full QoS profile — see session 3, where it
starts to matter).

`create_timer(0.1, ...)` calls the callback every 100 ms. Publishing from a
timer rather than a loop keeps the node responsive.

### A subscriber

```python
#!/usr/bin/env python3

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MySubscriber(Node):

    def __init__(self):
        super().__init__('myfirstsubscriber')
        self.subscription = self.create_subscription(
            String, 'myfirsttopic', self.listener_callback, 10)

    def listener_callback(self, msg):
        self.get_logger().info(f'I heard: {msg.data}')


def main():
    rclpy.init()
    node = MySubscriber()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
```

`create_subscription` takes the type, the name, the **callback** that runs on
each message, and the queue depth.

:::{tip}
Use `self.get_logger().info(...)` rather than `print(...)`. Logger output gets
timestamps and node names, can be filtered by severity, and is captured in
launch logs — all of which you will want in session 8.
:::

### Inspecting topics

```bash
ros2 topic list                          # all topics
ros2 topic echo /myfirsttopic            # print messages as they arrive
ros2 topic info -v /myfirsttopic         # types, publishers, subscribers, QoS
ros2 topic hz /myfirsttopic              # actual publishing rate
ros2 interface show std_msgs/msg/String  # what is in this message type?
```

These four commands solve most "why is nothing happening?" problems. Learn them
now; you will use them every single session.

## Parameters

A parameter is a node's configuration: a value you can read and change without
editing code. Every node has parameters, and every parameter is reconfigurable
at runtime.

### From the command line

```bash
ros2 param list
ros2 param get /turtlesim background_g
ros2 param set /turtlesim background_g 177
```

:::{tip}
Setting the turtlesim background to `background_r: 0`, `background_g: 177`,
`background_b: 172` gives you FH Aachen mint green.
:::

### In a node

```python
node.declare_parameter('my_param', 13)
value = node.get_parameter('my_param').value
```

Declaring a parameter fixes its name, type and default at startup, which means
a typo produces a clear error rather than a silently missing value.

## Launch files

A robot is a dozen nodes. Starting them by hand, in order, in a dozen terminals
is not a workflow. A **launch file** starts them together.

ROS 2 supports YAML, XML and Python launch files. YAML is the most readable for
simple cases:

```yaml
launch:

- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    name: "sim"

- node:
    pkg: "turtlesim"
    exec: "turtlesim_node"
    name: "new_sim"
    namespace: "new_turtle"
    param:
    -
      name: "background_r"
      value: 0
    -
      name: "background_g"
      value: 177
    -
      name: "background_b"
      value: 172
```

Note `name` and `namespace`: the same executable is started twice, under two
different node names, and the second in its own namespace so its topics do not
collide with the first.

### Installing launch files

Launch files must be installed to be found. Once per package, add to
`setup.py`:

```python
import os
from glob import glob

# ... inside setup(), in data_files:
(os.path.join('share', package_name, 'launch'), glob('launch/*.launch.*')),
```

Then place launch files in a `launch/` directory in the package, build, and
run:

```bash
ros2 launch my_first_package turtle.launch.yaml
```

### Composing launch files

Launch files can include other launch files, which is how a real robot bringup
is structured — one top-level file per robot, including one file per subsystem:

```yaml
launch:

- include:
    file: "$(find-pkg-share robot_bringup)/launch/sensors.launch.yaml"

- include:
    file: "$(find-pkg-share robot_bringup)/launch/navigation.launch.py"
```

Python launch files are more verbose but allow logic — arguments, conditions,
computed paths. A common and sensible pattern is YAML for the simple files and
Python where you need arguments:

```python
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource


def generate_launch_description():
    lidar_share = get_package_share_directory('rplidar_ros')

    return LaunchDescription([
        IncludeLaunchDescription(
            PythonLaunchDescriptionSource(
                os.path.join(lidar_share, 'launch', 'rplidar_c1_launch.py')
            ),
            launch_arguments={'frame_id': 'laser_frame'}.items()
        ),
    ])
```

:::{tip}
Build one `robot_bringup` package early and grow it through the course. By
session 8 a single `ros2 launch robot_bringup robot.launch.yaml` should start
your whole robot — that is the goal.
:::

## Services and actions, briefly

Topics are a continuous stream with no reply. Two other patterns cover what
topics cannot.

**Service** — a request and a response, like a function call across the
network. Use it for something quick with an answer: *stand up*, *reset the
odometry*, *save the map*. The caller waits.

```bash
ros2 service list -t
ros2 interface show std_srvs/srv/Empty
ros2 service call /my_service std_srvs/srv/Empty "{}"
```

**Action** — a long-running task with feedback and the ability to cancel. Use
it when the answer takes time and you want progress in the meantime: *navigate
to this pose*, *move the arm along this trajectory*.

```bash
ros2 action list
ros2 action info /navigate_to_pose
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose "<goal>"
```

Choosing between them:

```{list-table}
:header-rows: 1
:widths: 20 26 27 27

* -
  - Topic
  - Service
  - Action
* - Pattern
  - Stream, no reply
  - Request → response
  - Goal → feedback → result
* - Duration
  - Continuous
  - Immediate
  - Seconds to minutes
* - Cancellable
  - n/a
  - No
  - Yes
* - Example
  - `/scan`, `/cmd_vel`
  - Stand up, save map
  - Navigate to a pose
```

Session 7 uses actions properly. For now, recognising which is which is enough.

   Change it at runtime with `ros2 param set` and watch the output change

**Part 3 — Drive something.**

Make your publisher publish `geometry_msgs/msg/Twist` on your robot's velocity

constant `angular.z` is a circle.

Check your platform page for the correct topic name — it is `/cmd_vel` on most
systems but not all.
:::

:class: result

`ros2 topic echo` shows your messages. `ros2 param set` changes the published

In part 3, the robot — real or simulated — drives a circle and returns roughly

:::

:::{dropdown} Hint: driving a circle
:icon: light-bulb

```python
from geometry_msgs.msg import Twist

# in __init__
self.publisher = self.create_publisher(Twist, '/cmd_vel', 10)
self.create_timer(0.1, self.timer_callback)

# in the callback
msg = Twist()
msg.linear.x = 0.2      # m/s forward
msg.angular.z = 0.4     # rad/s turn
self.publisher.publish(msg)
```

The radius is `linear.x / angular.z`. Start slow — 0.2 m/s is plenty.

Always publish a zero `Twist` before shutting the node down, or the robot
keeps the last command.
:::

## Common mistakes

**The node runs but nothing is published.**
No `rclpy.spin()`, so no callback ever fires. Or you created the publisher as a
local variable in a function and it was garbage-collected.

**`Package 'x' not found` right after building it.**
You did not source `install/setup.bash`, or you are in a terminal opened before
the build.

**The subscriber receives nothing.**
Check the topic name character by character with `ros2 topic list`. A namespace
or a leading slash is the usual culprit: `cmd_vel` and `/cmd_vel` are different
topics.

**Changing the code has no effect.**
You did not rebuild. `colcon build --symlink-install` makes Python changes take
effect without rebuilding, which is worth using during development.

**Two nodes with the same name.**
ROS 2 allows it and the results are confusing. Give each node a distinct name,
or use namespaces.

**The robot keeps driving after `Ctrl` + `C`.**
Nothing told it to stop. The last `Twist` stands until something overrides it.
Publish zeros before exiting.
